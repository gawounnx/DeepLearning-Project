## Problem Statement

보험 약관 같은 **약관**은 수십 쪽에 걸쳐 의무·권리·조건·예외가 여러 **조항**에 흩어져 있다. **고객**은 "보험금을 언제 받을 수 있는지, 어떤 경우에 못 받는지, 내게 불리한 조항이 있는지"를 알고 싶지만, 조항 사이의 연결(예: 지급 조항 ↔ 면책 조항)을 직접 따라가기 어렵고, 어떤 조항이 약관법상 문제가 될 수 있는지 판단할 기준도 없다.

반대로 약관을 만드는 **사업자** 입장에서는 자신의 약관 중 무효·시정 위험이 있는 조항을 미리 점검할 수단이 마땅치 않다.

기존 요약·키워드 도구는 "어떤 조항이 왜 불리한지"를 **원문 근거**와 **판단 근거**로 연결해 주지 못하고, 조항 간 관계 구조도 보여주지 않는다.

## Solution

**이용자**가 약관(또는 개별 계약서) PDF·DOCX를 올리면, LawLens는

1. 문서를 조항 단위로 나누고,
2. 조항에서 당사자·의무·권리·조건·예외·금액·기한 관계를 뽑아 **관계 그래프**로 보여주며,
3. 약관이라면 조항마다 **불리 판정**을 내려 🔴 **불리 조항** / 🟡 **확인 필요** / 표시 없음 3단계로 표시하고,
4. 🔴·🟡 조항에는 **관련 조문**(약관법 제6~14조) 후보와 **참조 사례**를, 🔴 조항에는 참조 사례의 **판단 근거**를 쉬운 말로 요약해 붙인다.

모든 관계와 판정은 업로드 문서 안의 원문 근거(페이지·조항·문장)로 거슬러 올라갈 수 있다. 왼쪽 원문 뷰어와 오른쪽 그래프는 서로 연동된다.

**검토 관점**을 고객(기본값)에서 사업자로 바꾸면, 같은 판정이 "불리할 수 있는 조항" 대신 "무효·시정 위험이 있는 조항"으로 읽힌다. 개별 계약서는 약관법이 적용되지 않으므로 불리 판정 없이 조항 구조와 관계 그래프만 보여준다(ADR 0004).

LawLens는 위법 여부를 확정하지 않는 **문서 분석 보조 도구**이며, 화면에 이를 명시한다.

## User Stories

### 업로드와 문서 유형

1. 이용자로서, 약관 PDF 파일을 올리고 싶다, 그래야 종이로 읽지 않고도 내용을 분석받을 수 있다.
2. 이용자로서, 약관 DOCX 파일도 올리고 싶다, 그래야 워드로 받은 약관도 같은 방식으로 분석할 수 있다.
3. 이용자로서, 업로드할 때 문서 유형(약관 / 개별 계약서)을 직접 고르고 싶다, 그래야 문서 성격에 맞는 분석을 받을 수 있다.
4. 이용자로서, 문서 유형 선택란에 시스템이 추정한 기본값이 미리 채워져 있으면 좋겠다, 그래야 대부분의 경우 확인만 하고 넘어갈 수 있다.
5. 이용자로서, 지원하지 않는 형식(HWP, 이미지, 스캔 PDF)을 올리면 이유가 담긴 안내를 받고 싶다, 그래야 어떤 파일을 다시 준비해야 할지 안다.
6. 이용자로서, 문서가 너무 길어(페이지·조항 수 상한 초과) 분석할 수 없으면 업로드 단계에서 상한과 함께 안내를 받고 싶다, 그래야 몇 분 기다린 뒤 실패하지 않는다.
7. 이용자로서, 조·항 구조를 전혀 인식할 수 없는 문서를 올리면 "조항 구조를 인식할 수 없는 문서"라는 안내를 받고 싶다, 그래야 엉뚱한 분석 결과를 믿지 않는다.
8. 이용자로서, 업로드할 때 검토 관점(고객 / 사업자)을 고를 수 있으면 좋겠다, 그래야 처음부터 내 입장에 맞는 문구로 결과를 볼 수 있다.
9. 이용자로서, 분석이 진행되는 동안 진행 상태(파싱 → 판정 → 관계 추출)를 보고 싶다, 그래야 몇 분 걸리는 분석을 기다릴 수 있다.
10. 이용자로서, 분석이 실패하면 무엇이 실패했는지 알려주는 메시지와 재시도 버튼을 보고 싶다, 그래야 처음부터 다시 업로드하지 않아도 된다.

### 원문 보기

11. 이용자로서, 올린 문서를 원래 모양 그대로 화면 왼쪽에서 보고 싶다, 그래야 분석 결과를 원문과 대조할 수 있다.
12. 이용자로서, DOCX로 올린 문서도 PDF와 똑같은 뷰어로 보고 싶다, 그래야 형식마다 다른 화면에 적응하지 않아도 된다.
13. 이용자로서, 문서가 조·항 단위로 나뉜 조항 목록을 보고 싶다, 그래야 원하는 조항으로 바로 이동할 수 있다.
14. 이용자로서, 조항을 선택하면 원문 뷰어가 그 페이지로 이동하고 조항 영역이 강조되면 좋겠다, 그래야 긴 문서에서 위치를 찾느라 헤매지 않는다.

### 불리 판정 (약관)

15. 고객 관점 이용자로서, 조항마다 🔴 불리 조항 / 🟡 확인 필요 / 표시 없음 중 하나가 표시되면 좋겠다, 그래야 먼저 읽어야 할 조항을 알 수 있다.
16. 고객 관점 이용자로서, 불리 조항만(또는 확인 필요까지) 모아 보는 필터를 쓰고 싶다, 그래야 수십 개 조항 중 핵심만 빠르게 검토할 수 있다.
17. 고객 관점 이용자로서, 불리 조항에 관련 조문(예: 약관법 제7조 면책조항의 금지)이 붙어 있으면 좋겠다, 그래야 어떤 법적 쟁점과 연결되는지 안다.
18. 고객 관점 이용자로서, 불리 조항이 왜 불리한지 쉬운 말로 된 판단 근거 요약을 보고 싶다, 그래야 법률 지식이 없어도 이해할 수 있다.
19. 고객 관점 이용자로서, 판단 근거 요약이 어떤 참조 사례(비슷한 조항과 그 판단, 심결례 여부)에서 왔는지 펼쳐 보고 싶다, 그래야 요약을 그대로 믿지 않고 직접 확인할 수 있다.
20. 고객 관점 이용자로서, 확인 필요 조항에는 "모델이 판단을 확신하지 못함, 직접 확인 권장" 설명과 함께 관련 조문 후보와 참조 사례를 펼쳐 볼 수 있으면 좋겠다, 그래야 무엇을 기준으로 확인할지 안다.
21. 고객 관점 이용자로서, 판정의 불리 확률을 볼 수 있으면 좋겠다, 그래야 판정 강도를 가늠할 수 있다.
22. 고객 관점 이용자로서, 불리 조항과 확인 필요 조항이 하나도 없으면 "검토 대상으로 표시된 조항이 없습니다(누락 가능성 있음)" 안내를 보고 싶다, 그래야 빈 화면을 오류로 오해하지 않는다.
23. 이용자로서, 화면 어디서든 "이 결과는 법률 자문이 아니며 위법 여부를 확정하지 않는다"는 안내를 볼 수 있어야 한다, 그래야 결과를 과신하지 않는다.

### 검토 관점

24. 사업자 관점 이용자로서, 같은 판정을 "무효·시정 위험이 있는 조항, 수정 권장"이라는 문구로 보고 싶다, 그래야 내 약관을 점검하는 데 쓸 수 있다.
25. 이용자로서, 분석 화면에서 검토 관점을 바꾸면 재분석 없이 문구만 즉시 바뀌면 좋겠다, 그래야 두 입장을 빠르게 비교할 수 있다.
26. 이용자로서, 현재 어떤 검토 관점으로 보고 있는지 화면에 항상 표시되면 좋겠다, 그래야 문구를 오해하지 않는다.

### 관계 그래프

27. 이용자로서, 화면 오른쪽에서 당사자·의무·권리·조건·예외·금액·기한·조항이 노드로 연결된 관계 그래프를 보고 싶다, 그래야 문서 전체 구조를 한눈에 파악할 수 있다.
28. 이용자로서, 노드 유형마다 색과 모양이 다르면 좋겠다, 그래야 의무와 권리, 조건과 예외를 구분할 수 있다.
29. 이용자로서, 간선에 "부담한다 / 가진다 / 조건 / 예외 / 한도·기한 / 참조" 같은 관계 이름이 보이면 좋겠다, 그래야 노드 사이 의미를 알 수 있다.
30. 이용자로서, 그래프의 노드나 간선을 클릭하면 왼쪽 원문 뷰어가 그 원문 근거가 있는 조항으로 이동해 강조되면 좋겠다, 그래야 관계가 실제로 문서에 있는지 확인할 수 있다.
31. 이용자로서, 왼쪽에서 조항을 선택하면 그 조항에서 나온 노드와 간선이 그래프에서 강조되면 좋겠다, 그래야 조항이 다른 조항과 어떻게 이어지는지 볼 수 있다.
32. 이용자로서, 불리 조항에서 나온 의무·권리·조건·예외·금액·기한 노드가 그래프에서 따로 표시되면 좋겠다, 그래야 불리 조항이 어떤 관계와 얽혀 있는지 추적할 수 있다.
33. 이용자로서, 특정 당사자(예: 보험회사)를 선택해 그 당사자의 의무·권리만 보고 싶다, 그래야 "회사가 해야 하는 것"과 "내가 해야 하는 것"을 나눠 볼 수 있다.
34. 이용자로서, 노드를 당사자 중심으로 접고 펼칠 수 있으면 좋겠다, 그래야 조항이 많은 약관에서도 그래프가 읽힌다. (선택 기능)
35. 이용자로서, 약관에서 당사자마다 사업자/고객/기타 역할 배지가 붙어 보이면 좋겠다, 그래야 문서마다 다른 명칭(회사, 계약자 등)에 헷갈리지 않는다.
36. 보험 약관 이용자로서, 보험계약자·피보험자·보험수익자가 하나로 합쳐지지 않고 각각의 노드로 보이면 좋겠다, 그래야 보험금이 누구에게 가는지 정확히 알 수 있다.
37. 이용자로서, 원문에서 원문 근거 문장을 찾을 수 없는 관계는 그래프에 나오지 않기를 원한다, 그래야 지어낸 관계를 믿게 되지 않는다.
38. 이용자로서, 문서 안에 없는 조항이나 다른 법령(예: 상법 제651조)을 가리키는 표현이 잘못된 참조 간선으로 그려지지 않기를 원한다, 그래야 그래프를 믿을 수 있다.

### 개별 계약서

39. 개별 계약서를 올린 이용자로서, 불리 판정 없이 조항 구조와 관계 그래프를 보고 싶다, 그래야 약관이 아닌 계약서의 구조도 파악할 수 있다.
40. 개별 계약서를 올린 이용자로서, 왜 불리 판정이 없는지 안내를 받고 싶다(약관법은 약관에만 적용), 그래야 기능 누락으로 오해하지 않는다.
41. 개별 계약서를 올린 이용자로서, 당사자가 문서에 적힌 명칭(갑, 을 등) 그대로 보이면 좋겠다, 그래야 원문과 대조하기 쉽다.

### 결과 다시 보기

42. 이용자로서, 분석이 끝난 문서를 목록에서 다시 열고 싶다, 그래야 같은 문서를 매번 재분석하지 않아도 된다.

### 개발자(팀원)와 평가

43. 개발자로서, 실험 E0~E3을 같은 데이터 분할·같은 지표·여러 시드로 다시 돌릴 수 있으면 좋겠다, 그래야 Baseline 대비 향상이 시드 운이 아님을 보여줄 수 있다.
44. 개발자로서, 텍스트 길이만 쓰는 기준선의 성능을 함께 보고 싶다, 그래야 모델이 조항 길이·형식 같은 지름길로 유불리를 맞히는지 확인할 수 있다.
45. 개발자로서, 보정 전후 기대 보정 오차와 클래스별 Conformal 실제 포함률·🟡 비율을 리포트로 받고 싶다, 그래야 "실제 불리 조항의 90% 이상을 🔴 또는 🟡로 잡는다"는 약속을 지키는지 확인할 수 있다.
46. 개발자로서, 관계 정답셋으로 관계 추출 품질(엄격·완화 기준 P/R/F1, JSON 유효율, 원문 검증 통과율, 조항당 처리 시간)을 측정하고 싶다, 그래야 E5 결과를 수치로 발표할 수 있다.
47. 개발자로서, 분석 결과에 모델 버전과 보장 수준이 기록되면 좋겠다, 그래야 어떤 설정으로 나온 결과인지 추적할 수 있다.
48. 개발자로서, 노트북에서 SSH로 Lab 서버의 웹 화면에 접속해 데모를 할 수 있으면 좋겠다, 그래야 GPU 없는 노트북으로도 라이브 시연을 할 수 있다.

## Implementation Decisions

### 전체 구조

- 모든 서비스(백엔드, 모델, LLM 서버, 프론트 빌드)는 Lab 서버(RTX 5090 32GB, CUDA 12.8 이상, PyTorch 2.7 이상)에서 돌린다. 발표 때는 노트북에서 SSH 포트 포워딩으로 웹 화면에 접속한다. 클라우드 배포, 인증, 다중 이용자는 없다.
- 스택: 백엔드 FastAPI(Python) · DOCX→PDF 변환 LibreOffice headless · 문서 파싱 PyMuPDF(단일 파이프라인) · 프론트 React + Vite + TypeScript · 그래프 Cytoscape.js · 뷰어 PDF.js(react-pdf) · LLM 서빙 vLLM · 저장 SQLite 또는 문서별 JSON.
- 외부 LLM API는 쓰지 않는다(ADR 0002).
- **GPU 사용 규칙**: GPU가 한 장이므로 RoBERTa 학습과 EXAONE 서빙을 동시에 올리지 않는다. 학습과 프롬프트 개발 시간대를 나눠 GPU 사용 시간표로 관리하고, 작은 실험(E0, E1, 길이 기준선)은 필요하면 Colab T4로 돌린다. 데모·통합 시점에는 EXAONE(메모리 상한 설정)과 RoBERTa 추론만 함께 올린다.

### 모듈

1. **문서 수집·파싱 모듈** (차가원)
   - 입력: PDF(텍스트 레이어 필수) 또는 DOCX. DOCX는 업로드 즉시 LibreOffice로 PDF 변환한 뒤 이후 모든 처리(텍스트 추출, 조항 분할, 위치 계산)를 **변환된 PDF 하나로** 한다. Word 자동 번호("제1조" 등)도 변환본에 글자로 남으므로 이 방식이 더 안정적이다.
   - 거절 조건: 텍스트를 추출할 수 없는 PDF(스캔 PDF), 지원하지 않는 형식, 상한 초과(초기값 50페이지·250개 조항, 1주 차 처리 시간 측정 후 확정), 조항 분할 결과 0개.
   - 조항 분할: "제N조(제목)", 원문자 항 번호(①②…), 숫자 항 표기를 인식해 조·항 단위 조항으로 나눈다. 각 조항은 조 번호, 항 번호(없을 수 있음), 조 제목(없을 수 있음), 페이지, 원문, 조항 영역 좌표(페이지별 사각형 목록)를 가진다.
   - 강조 방식: 기본은 **조항 영역 강조 + 해당 페이지 스크롤**이다. 원문 근거 문장 단위 강조는 PDF 텍스트 검색으로 찾을 수 있을 때만 덧붙인다(실패해도 조항 영역 강조는 유지).
   - 문서 유형 추정: 규칙 기반(예: "약관", "보통약관", "회사는…계약자" 패턴 vs "갑", "을", 서명란). 결과는 업로드 화면의 기본값 제안에만 쓴다(ADR 0004).

2. **불리 판정 모듈** (고용민) — 약관에만 실행
   - 모델 구성: **두 모델을 따로 학습**한다.
     - 이진 모델: 전체 데이터로 유리/불리 분류.
     - 관련 조문 모델: 불리 샘플만으로 약관법 제6~14조 **다중 라벨** 분류(한 조항에 여러 조문 가능, 조문별 시그모이드).
     - 기본 인코더는 KLUE-RoBERTa-large이며, 최종 채택 모델은 E1~E3 결과로 정한다.
   - 입력 길이: 최대 512토큰. 넘으면 **앞 128 + 뒤 382 토큰(head+tail)**으로 자른다. 면책 단서가 조항 끝에 오는 경우가 많기 때문이다. 학습과 추론에 같은 규칙을 쓴다.
   - 출력(조항별): 불리 확률(보정 후, 화면 표시용), 예측 집합, 표시 단계, 관련 조문 후보와 확률(🔴·🟡 조항), 조항 의미 벡터.
   - 표시 단계 결정(ADR 0003 개정판):
     - **클래스 조건부(Mondrian) split conformal prediction**, 보장 수준 90%. 유리·불리 각 클래스의 보정 데이터로 기준값을 따로 구한다.
     - 예측 집합 → 표시 단계: {불리} → 🔴 불리 조항 / {유리, 불리} 또는 빈 집합 → 🟡 확인 필요 / {유리} → 표시 없음.
     - 의미: 실제 불리 조항의 90% 이상이 🔴 또는 🟡로 표시된다.
     - 온도 스케일링은 **화면에 보이는 불리 확률과 보정 오차 개선용**이다. 이진 분류에서는 온도 스케일링이 클래스 확률의 순서를 바꾸지 않으므로 예측 집합에 영향이 없다.
     - 보장 수준은 설정값이며 이용자가 바꿀 수 없다.

3. **참조 사례 검색 모듈** (고용민)
   - 이진 모델 마지막 층의 평균 풀링 벡터(L2 정규화)로, 학습 분할의 불리 조항들을 색인한다.
   - 🔴·🟡 조항마다 코사인 유사도 상위 k개(기본 3) 참조 사례를 찾고, 각 사례의 조항 원문·분야·위법성 판단 근거·관련 법령·공정위 심결례 해당 여부·비교 근거·유사도를 돌려준다.

4. **판단 근거 요약 모듈** (고용민) — 🔴 불리 조항에만 실행
   - EXAONE에 불리 판정 결과, 관련 조문 후보, 참조 사례의 판단 근거만 넣고 2~4문장 요약을 받는다. 요약은 넣어준 판단 근거 밖의 법령이나 사실을 만들면 안 된다.
   - 검증: 요약에 등장한 **모든 법령 조문 표기**(약관법, 상법 등)가 입력한 관련 조문 후보나 참조 사례의 관련 법령에 없으면, 요약을 버리고 참조 사례 원문만 보여준다.

5. **관계 추출 모듈** (차가원)
   - 모델: EXAONE 4.5 33B AWQ(4비트), vLLM 서빙, 추론 모드 끔. 대체 모델은 EXAONE 3.5 7.8B Instruct(ADR 0002). 두 모델은 채팅 옵션이 다르므로(3.5는 추론 모드 옵션이 없음) LLM 호출부는 모델별 옵션을 감싸는 공통 인터페이스로 만든다.
   - 단일 5090 서빙 제약:
     - 공식 예시 설정은 GPU 2장·256K 컨텍스트 기준이다. 우리는 컨텍스트 상한을 조항 단위 작업에 맞게 줄이고(예: 8K), 이미지 입력을 0으로 막고, GPU 메모리 사용률 상한을 둬서 RoBERTa 추론 몫을 남긴다.
     - transformers·vLLM 버전은 모델 카드 요건을 따르며, 설치 시 실제 버전으로 확인한다.
   - 처리 방식: 조항 단위로 지시문 + 조항 원문 + 출력 형식을 주고 JSON으로 관계를 받는다.
     - 조항 요청은 동시성 상한을 둔 **동시 요청**으로 보내 vLLM 연속 배칭을 활용한다.
     - 가능하면 vLLM 구조화 출력 기능으로 형식을 강제한다. 모델이 `\boxed{}` 형식을 선호하므로, 지시문에 "JSON만 출력"을 명시한다.
   - 응답 처리: 마크다운 코드 펜스 등을 벗긴 뒤 JSON으로 파싱한다. 실패하면 1회 재시도하고, 그래도 실패하면 그 조항을 "관계 없음"으로 처리한다.
   - 원문 검증: 각 관계의 원문 근거 문장이 해당 조항 원문에 (공백·줄바꿈 정규화 후) 그대로 들어 있지 않으면 버린다.
   - 당사자 역할 부여:
     - LLM은 문서 속 당사자 명칭만 추출한다.
     - 약관이면 규칙 사전으로 역할을 붙인다: 회사·보험회사·보험자 → 사업자 / 계약자·보험계약자 → 고객 / 그 외(피보험자, 보험수익자 등) → 기타.
     - 개별 계약서는 역할 없이 문서 명칭 그대로 둔다.
   - 조항 간 참조: "제N조", "제N조 제M항"을 정규식으로 찾는다. 앞에 법령명이 붙은 표현("상법 제651조", "같은 법", "법 제N조")은 제외한다. 파싱된 조항 중 대상이 있을 때만 참조 간선을 만든다.

6. **그래프 구성 모듈** (차가원)
   - 노드 8종: 당사자, 의무, 권리, 조건, 예외, 금액, 기한, 조항.
   - 간선 7종: 부담한다(당사자→의무), 가진다(당사자→권리), 조건(의무·권리→조건), 예외(의무·권리→예외), 한도·기한(의무·권리→금액·기한), 참조(조항→조항), 원문 근거(관계 노드→조항).
   - 당사자 노드는 **정규화한 명칭별로 하나**씩 만든다(보험계약자·피보험자·보험수익자는 서로 다른 노드). 역할(사업자/고객/기타)은 노드 속성(배지)이다. 의무·권리 등은 조항별로 따로 두고 조항 간 병합은 하지 않는다.
   - "불리 조항 연결" 표시는 🔴 조항과 원문 근거 간선으로 연결된 **당사자 외 관계 노드**(의무·권리·조건·예외·금액·기한)에만 붙인다.

7. **분석 서비스(API) 모듈** (고용민, 차가원의 파싱·관계 추출 모듈 연동)
   - 문서 등록: 파일 + 문서 유형을 받아 문서 ID를 돌려준다. 형식·상한 위반은 이 단계에서 거절한다.
   - 분석 시작: 문서 ID로 비동기 분석 작업을 시작한다. 단계는 파싱 → 불리 판정(약관만) → 참조 사례·판단 근거 요약(약관만) → 관계 추출 → 그래프 구성 → 완료.
   - 상태 조회: 현재 단계, 진행률, 그리고 실패 시 실패 단계·오류 메시지.
   - 재시도: 실패한 작업을 같은 문서로 다시 시작한다.
   - 결과 조회: 아래 분석 결과 구조를 돌려준다.
   - 원본 보기: 뷰어용 PDF(DOCX는 변환본)를 돌려준다.
   - 문서 목록: 이전에 분석한 문서와 상태.
   - 검토 관점은 API 파라미터가 아니다. 판정은 관점과 무관하며, 문구 전환은 프론트에서 한다.

8. **프론트엔드** (차가원)
   - 업로드 화면: 파일 선택, 문서 유형 선택(추정값 미리 선택), 검토 관점 선택(약관일 때만, 기본값 고객), 미지원 형식·상한 초과 안내.
   - 분석 화면 왼쪽:
     - PDF 뷰어(조항 영역 강조), 조항 목록, 판정 패널.
     - 판정 패널 내용: 표시 단계 배지, 불리 확률, 관련 조문 후보, 🔴의 판단 근거 요약, 펼치면 참조 사례.
     - 필터: 불리 조항만 / 확인 필요 포함 / 전체.
   - 분석 화면 오른쪽: Cytoscape 그래프, 노드 유형별 스타일, 역할 배지, 당사자 선택 필터. 당사자 중심 접기·펼치기는 선택 기능.
   - 양방향 연동: 그래프 선택 → 원문 조항 강조·스크롤 / 조항 선택 → 그래프 강조.
   - 검토 관점 × 표시 단계 문구 매핑은 순수 함수로 분리한다.
     - 고객: "불리할 수 있는 조항"
     - 사업자: "무효·시정 위험이 있는 조항, 수정 권장"
   - 상태 화면: 진행 단계 표시, 실패 메시지와 재시도, 🔴·🟡이 0건일 때 안내, 개별 계약서 안내("약관법은 약관에만 적용되어 불리 판정을 제공하지 않습니다").
   - 법률 자문 아님 안내를 상시 노출한다.

### 분석 결과 구조 (API 계약)

- **문서**: ID, 파일명, 문서 유형(약관 / 개별 계약서), 페이지 수, 분석 상태(진행 단계 / 완료 / 실패), 실패 시 실패 단계·오류 메시지.
- **조항 목록**: 각 조항마다
  - 조항 ID, 조 번호, 항 번호, 조 제목, 페이지, 원문, 영역 좌표 목록
  - 판정(약관만):
    - 불리 확률, 예측 집합, 표시 단계
    - 관련 조문 후보(조문·확률, 🔴·🟡만)
    - 판단 근거 요약(🔴만, 없을 수 있음)
    - 참조 사례 목록(🔴·🟡만): 원문, 분야, 위법성 판단 근거, 관련 법령, 심결례 해당 여부, 비교 근거, 유사도
- **그래프**:
  - 노드: ID, 유형, 라벨, 원래 명칭, 역할(사업자/고객/기타, 약관의 당사자만), 원문 근거 목록(조항 ID + 문장), 불리 조항 연결 여부
  - 간선: 출발, 도착, 유형, 원문 근거
- **메타**: 분류 모델 버전, LLM 모델 버전, 보장 수준, 분석 시각, 단계별 처리 시간.

### 데이터와 실험 (고용민)

- **데이터**: AI Hub「법률/규정(판결서, 약관 등) 텍스트 분석 데이터」 중 약관 부분(약 1만 건, 43개 분야, 보험 분야 약 1,355건). 승인 전에는 샘플 데이터로 스키마를 파악하고 파이프라인 코드를 먼저 작성한다.
- **1주 차 데이터 점검**(결과에 따라 아래 설계 확정):
  1. 출처 약관을 식별할 수 있는 정보(파일명, 폴더 구조 등)가 있는지 확인한다. 공개 페이지의 라벨 필드에는 문서 식별자가 없다.
  2. 중복·근사 중복 조항을 탐색한다. 같은 표준약관이 여러 회사에서 쓰이면 거의 같은 조항이 반복될 수 있다.
  3. 유리/불리별 조항 길이·형식 분포를 비교하고, 유리/불리 데이터가 구축 단위(조항 하나 vs 여러 조항 묶음)부터 다른지 확인한다.
  4. 관련 법령 필드에 조문이 여러 개 적힌 비율과 조문별 표본 수를 확인한다.
  5. 조 제목 포함 여부를 확인한다.
- **분할**:
  - 비율은 학습 70 / 검증 10 / 보정 10 / 테스트 10이며, 분야와 라벨로 층화한다. 검증은 모델 선택·조기 종료·온도 스케일링에, 보정은 Conformal에, 테스트는 최종 보고에만 쓴다.
  - 출처 식별 정보가 있으면 같은 출처 약관의 조항이 한 분할에만 들어가도록 그룹 층화 분할을 쓴다.
  - 없으면 분할 전에 정규화 후 완전 일치 조항을 제거하고, 분할 간 근사 중복 조항을 제거한다.
- **라벨 구성**:
  - 이진: 유불리 판단 필드(1 유리 / 2 불리).
  - 관련 조문(다중 라벨): 관련 법령 필드에서 약관법 제6~14조 조문 번호를 모두 추출해 라벨 집합으로 만든다.
    - 약관법 제6~14조 밖의 법령(상법, 약관법 제3·5조 등)은 라벨로 쓰지 않고, 참조 사례 정보로만 남긴다.
    - 표본이 너무 적은 조문은 "기타"로 묶는다(기준은 1주 차 점검 후 확정).
    - 제6~14조가 하나도 없는 불리 샘플은 관련 조문 학습에서 제외한다.
  - 데이터의 '불리한 조항 유형' 필드(값 2개)는 분류 대상으로 쓰지 않는다(ADR 0001).
- **실험**:
  - L0 길이 기준선: 조항 길이 등 형식 특징만 쓰는 분류기. 이 기준선의 성능이 높으면 지름길 학습 가능성으로 보고하고 데이터를 보완한다.
  - E0 TF-IDF + SVM
  - E1 KLUE-RoBERTa-base
  - E2 KLUE-RoBERTa-large
  - E3 E2 + 메타정보. 조 제목이 데이터에 있으면 조 제목만 쓴다. 이 경우 파서가 추출할 수 있어 추론 때도 같은 입력이 가능하다. 약관 분야를 쓰는 변형은 E3이 최종 채택될 때만 업로드 화면에 분야 선택을 추가한다는 조건으로 실험한다.
  - (선택, W5) 보험 분야만 따로 평가·학습해 전체 학습과 비교
  - E5 관계 추출 평가(EXAONE 단독)
- **지표와 보고 방식**:
  - 이진: Macro F1(주 지표), 정확도.
  - 관련 조문: 라벨별 Macro F1(주 지표), Micro F1, 라벨별 표본 수.
  - E1~E3은 시드 3개의 평균±표준편차로 보고하고, 핵심 비교(E1 vs E2, E2 vs E3)는 테스트셋 부트스트랩 95% 신뢰구간을 함께 낸다.
  - 보정: 보정 전후 기대 보정 오차(ECE).
  - Conformal: 클래스별 실제 포함률, 표시 단계별 비율(🟡·빈 집합 비율 포함). 비교 자료로 목표 지표 방식(🔴 정밀도 90%, 🔴+🟡 재현율 95%) 기준선 수치도 함께 낸다(ADR 0003).
  - (선택) 참조 사례 품질: 상위 3개 참조 사례의 관련 조문이 대상 조항의 관련 조문과 겹치는 비율.
- **관계 정답셋**(공동):
  - 보험 약관 조항 100~150개.
  - 주석 가이드(노드·간선 정의는 GLOSSARY.md와 위 스키마)를 먼저 쓴다.
  - 두 사람이 **LLM 출력을 보지 않고 독립적으로** 주석한 뒤 불일치를 협의해 확정한다. LLM 사전 주석은 쓰지 않는다. 평가 대상 모델의 출력에 정답이 끌려가는 것을 막기 위해서다.
  - 개별 계약서 정답셋은 만들지 않는다.
- **E5 채점 기준**(정답셋 주석자 간 일치도 계산에도 같은 기준을 쓴다):
  - 단위는 같은 조항 안의 관계 (주체, 관계 유형, 대상)이며, 조건·예외·금액·기한은 해당 관계에 붙은 별도 관계로 센다.
  - **엄격 일치**: 관계 유형이 같고, 주체 당사자의 정규화 명칭이 같고, 대상 라벨이 정규화(공백·문장부호 제거, 조사·어미 일부 제거) 후 같다.
  - **완화 일치**: 관계 유형과 주체가 같고, 대상 라벨의 글자 단위 F1이 0.5 이상이다.
  - 두 기준의 P/R/F1을 모두 보고하고, JSON 유효율·원문 검증 통과율·조항당 처리 시간을 함께 낸다.

### 데이터 취급

- 이용자가 올린 문서는 학습에 재사용하지 않는다. 데모와 시험에는 공개된 약관만 쓴다.

## Testing Decisions

### 좋은 테스트의 기준

- 외부에서 관찰되는 동작만 검증한다: "이 문서를 넣으면 이런 분석 결과가 나온다". 내부 함수 구조, 프롬프트 문구, 정규식 형태는 테스트하지 않는다.
- 모델 출력처럼 비결정적인 부분은 테스트에서 가짜(fake) 구현으로 바꿔 결정적으로 만들고, 실제 모델 품질은 테스트가 아니라 **평가 리포트**로 확인한다.
- 가짜 LLM은 정제된 객체가 아니라 **실제 모델처럼 원시 문자열**을 돌려준다. 정상 JSON, 코드 펜스로 감싼 JSON, 깨진 JSON, `\boxed{}`가 섞인 응답을 넣어서 응답 처리·재시도·원문 검증까지 경계 안에서 검증한다.

### 테스트 경계(seam)

1. **분석 서비스 경계 (주 경계, 하나로 유지)**
   - "문서 + 문서 유형 → 분석 결과 구조"를 API 수준에서 검증한다. 불리 판정 모듈과 LLM은 같은 인터페이스의 가짜 구현으로 바꿔 끼울 수 있게 만든다.
   - 이 경계 하나로 다음을 확인한다:
     - 파싱: 고정 PDF·DOCX 샘플을 넣으면 조항 수, 조·항 번호, 페이지가 기대값과 같다. DOCX와 같은 내용의 PDF는 같은 조항 목록을 낸다.
     - 거절: HWP·스캔 PDF·상한 초과·조항 0개 문서가 각각 명확한 오류로 거절된다.
     - 문서 유형: 개별 계약서는 판정 없이 그래프만 나오고, 당사자에 역할이 없다.
     - 표시 단계: 가짜 분류기가 돌려준 예측 집합({불리}, {유리, 불리}, 빈 집합, {유리})이 ADR 0003대로 표시 단계로 바뀐다. 🔴·🟡에만 관련 조문 후보·참조 사례가 붙는다.
     - 응답 처리: 코드 펜스·`\boxed{}`가 섞인 응답은 파싱되고, 깨진 JSON은 1회 재시도 후 "관계 없음"이 된다.
     - 원문 검증: 원문에 없는 원문 근거 문장이 담긴 관계는 그래프에 없다.
     - 요약 검증: 입력에 없는 법령 조문(약관법·상법 등)이 요약에 나오면 요약이 빠지고 참조 사례만 남는다.
     - 그래프:
       - 노드·간선 유형이 정해진 8종·7종 밖으로 나가지 않고, 모든 관계 노드에 원문 근거가 있다.
       - 보험계약자·피보험자는 서로 다른 당사자 노드다.
       - 당사자 노드에는 불리 조항 연결 표시가 붙지 않는다.
       - 문서에 없는 조항이나 외부 법령을 가리키는 참조는 간선이 되지 않는다.
     - 상태: 처리 중 실패를 주입하면 상태가 실패·실패 단계·오류 메시지로 바뀌고, 재시도하면 완료된다.
   - 같은 경계에서 실제 모델을 붙인 통합 실행을 Lab 서버에서 데모 약관 2개로 돌려, 오류 없이 끝나는지와 처리 시간을 기록한다.

2. **모델 평가 하네스 (테스트가 아닌 재현 가능한 평가)**
   - 고정 분할·고정 시드로 L0, E0~E3, 보정·Conformal 지표를 한 번에 다시 계산해 리포트로 남긴다.
   - 관계 정답셋으로 E5 지표(엄격·완화)를 계산한다.

3. **프론트 순수 함수 검증 (가벼움)**
   - 검토 관점 × 표시 단계 → 문구 매핑을 케이스별로 확인한다.

4. **데모 시나리오 스모크 테스트 (선택)**
   - Playwright로 "업로드 → 분석 완료 → 불리 조항 클릭 → 원문 강조 → 그래프 노드 클릭 → 원문 이동 → 검토 관점 전환" 흐름 하나를 자동 확인한다.

### 테스트 대상 모듈

- 분석 서비스 경계를 통해 문서 수집·파싱, 그래프 구성, 관계 추출 응답 처리(파싱·재시도·원문 검증·역할 부여·참조 처리), 판단 근거 요약 검증, 표시 단계 매핑, 작업 상태를 간접적으로 테스트한다.
- 불리 판정 모듈과 참조 사례 검색 모듈은 평가 하네스로 검증한다.

### 기존 사례

- 신규 프로젝트라 저장소에 기존 테스트가 없다. 첫 테스트를 분석 서비스 경계 테스트로 만들고 이후 테스트가 이를 따른다.

## Out of Scope

- 스캔 PDF·이미지 OCR, HWP 등 PDF·DOCX 외 형식
- 상한(초기값 50페이지·250개 조항)을 넘는 문서
- 개별 계약서의 불리 판정과 관련 조문, 개별 계약서 관계 정답셋
- 문서 유형 자동 판별 모델(규칙 기반 기본값 제안만 함), 약관 분야 자동 추정
- 사업자에게 불리한 조항 탐지(사업자 관점은 같은 판정의 문구 전환일 뿐)
- 위법 여부의 확정 판정, 법률 자문
- 관계 추출 모델 학습·파인튜닝, 다른 오픈 LLM과의 비교 실험, LLM 사전 주석
- 외부 LLM API(Claude, GPT 등)
- 국가법령정보센터 등 외부 법령의 실시간 조회(판단 근거는 데이터셋의 판단 근거 필드에서만 가져옴)
- 원문 근거 문장 단위의 정밀 강조 보장(조항 영역 강조가 기본)
- 클라우드 배포, 로그인·인증, 다중 이용자, 모바일 화면
- 이용자 업로드 문서의 학습 재사용
- SSH 연결 실패 대비 오프라인 모드

### 위험과 1주 차 확인 사항

- **AI Hub 승인 지연**: 승인 전에는 샘플 데이터로 파이프라인을 먼저 만든다. 샘플 데이터도 승인이 필요한지는 페이지에 명시되어 있지 않아 신청 시 확인한다.
- **데이터 중복·지름길**: 출처 식별 정보가 없으면 그룹 분할이 불가능하다. 근사 중복 제거와 L0 길이 기준선으로 대신 점검한다.
- **이진 분류 개선 폭**: AI Hub 보고 F1이 0.91이라 E0~E3 차이가 작을 수 있다. 관련 조문 분류를 주 비교 과제로 두고, 시드 평균과 신뢰구간으로 차이가 실제인지 보인다.
- **관련 조문 라벨 불균형**: 조문별 표본 수에 따라 "기타" 병합 기준을 정한다.
- **조 제목 필드 유무**: 없으면 E3은 분야 정보 변형만 남고, 채택 시 업로드 화면에 분야 선택이 추가된다.
- **EXAONE 4.5 단일 GPU 서빙**: 컨텍스트 상한·이미지 입력 차단·메모리 상한 설정으로 올라가는지, 동시 요청으로 데모 약관 1개가 3분 안에 끝나는지 1주 차에 측정해 대체 여부를 확정한다(ADR 0002).
- **GPU 경합**: 학습과 서빙이 한 장의 GPU를 나눠 쓴다. 시간표를 지키지 않으면 W2~W3 실험이 밀린다.
- **파싱 품질**: 약관 PDF는 다단·표·각주가 섞여 조항 분할이 깨질 수 있다. 데모 약관은 파싱 결과를 미리 확인한 문서로 고정한다.
