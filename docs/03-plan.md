## 2. 공통 파일과 병합 규칙

**공통 기반 담당(고용민)만 수정한다.** 다른 사람이 고쳐야 하면 먼저 알리고 승인을 받은 뒤 수정한다. 에이전트는 수정이 필요하면 멈추고 보고한다.

- SPEC「분석 결과 구조」(API 계약)와 공유 타입(백엔드 Pydantic 모델, 거기서 생성한 프론트 TS 타입)
- `pyproject.toml`, `uv.lock`, `frontend/package.json`, `frontend/package-lock.json` (충돌 시 직접 편집하지 말고 재설치로 다시 만든다)
- `.env.example`, 저장 방식(SQLite 또는 문서별 JSON)과 그 경로, FastAPI 라우터 구조

`docs/SPEC.md`(위 계약 절 제외), `docs/GLOSSARY.md`, `docs/adr/`는 지금처럼 **두 사람 합의**로 바꾼다.

**병합 규칙**

- 커밋과 푸시는 `main`에서 직접 진행한다(2026-11-08 사람 결정, AGENTS §7). 기능 브랜치와 PR은 필수가 아니다. 브랜치를 쓸 때 이름은 `feat/<티켓ID>-<짧은이름>`(예: `feat/W1-07c-clause-split`), PR을 쓸 때는 `.github/pull_request_template.md`의 확인 항목을 채운다.
- 푸시 전에 최신 `main`을 반영하고 관련 검사를 다시 실행한다. 통합 `verify`는 H-04c 이후 생긴다. 충돌 해결이 어려우면 병합 담당(차가원)이 맡는다. 강제 푸시는 하지 않는다.
- 사람 작업(신청·주석·협의)은 브랜치 없이 progress.md 메모로 증거를 남긴다.
